SentryGate · Progress Report 2 · Presenting cheat sheet

How to present to the panel

If the panel remembers one thing: a cache in front of a safety filter lets attacks through, because on a cache hit the filter is never asked. We proved it on our own system, and we know how to fix it.

Before you start (10 minutes before)

1. Start the demo (takes about a minute)

Open Docker Desktop first. Then in the project folder:
make demo-up
Wait for the line ready: ... | seeding on. It loads the real models and needs no internet or API key.

2. Open the slides

PowerPoint: SentryGate_Progress_Report_2.pptx, then Slide Show → Presenter View (notes on your screen).
Backup: the PDF of the same deck.

3. Keep the backup ready

Open docs/captures/gateway-week5.txt in a tab. If the live demo fails, show this and move on. Never debug on stage.

4. Split the talk

Speaker 1: slides 1–3 · Speaker 2: slides 4–6 · Speaker 3: slide 7 + demo, 8–11. The person who knows the code best does the demo and technical questions.

The live demo (slide 7)

Run

make gateway-demo

Narrate as it prints:
  1. Normal question: answered, then served from cache the second time.
  2. Attack, empty cache: BLOCKED. The filter works.
  3. Same attack after poisoning: served the harmful answer, screened = false. That's the hole, live.
  4. Name + email: flagged as personal data.

If they look confused: the analogy

It's like a bouncer (the filter) and a guest list (the cache). If your name is on the list, you walk straight in and the bouncer never checks you. Change your name slightly, and you're still on the list.

Likely questions

They askYou answer
Isn't the filter just weak?No. It catches every attack when asked (score 1.000). It's just never asked on a cache hit.
How do you know it didn't run?Every request writes a log line. For every bypass, the log says the filter didn't run.
Make the cache stricter?Slide 5: even the strictest setting leaks 90%.
Just check everything?Slide 6: seven times slower, and it throws away why the cache exists.
How did the bad answer get in?We planted it on purpose to model any leak. We measure whether it gets served, not how it got in.
Is this a real problem?Yes. OWASP's Top 10 for LLM apps flags it. We're the first we know of to measure it on a running system.
Real data?239 real attacks from two public datasets, reworded 2,838 ways.
Don't know the answer?"Good question. We haven't measured that yet. It's on our Phase 3 list." Never guess a number.

Five tips

  1. Result first, details second. "97% got through", then how.
  2. Point at the slide. Put the cursor on the exact number or bar you're talking about.
  3. Don't read every word. One idea per slide.
  4. Pause after the big numbers. Let "97%" and "zero" land.
  5. Be honest about limits. "That's Phase 3" sounds confident, not weak.
