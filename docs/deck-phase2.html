Where we left off

Phase 1 proved the problem in a script.

A cache hit returns before the safety filter is ever asked — so a reworded attack can be served an answer the filter would have blocked.

This checkpoint answers one question: does it happen on a real running system? It does.

What we built

A real gateway. This is what runs today.

OpenAI-compatible API behind nginx, in Docker. The cache is checked before the filter — that is the hole. The safety label is already saved with every answer, ready for the fix.

The experiment

239 real attacks, 2,838 rewordings, on the live gateway.

  • Seeds from two public datasets: deepset/prompt-injections and jayavibhav/prompt-injection.
  • Two families, kept apart: lazy edits (capitals, punctuation, a filler word) and full rewrites (real paraphrases).
  • Every variant fired over HTTP at the running gateway.

A bypass is counted only when both are true

The poisoned answer comes back, and

the gateway's own log line says screening_ran = false.

The claim is read from the log, not from our code.

Move the filter in front of the cache, same build, same attacks — the bypass drops to zero.

Why the cache goes first

A hit is 7× faster than a miss.

OutcomeRequestsp50p99
Cache hit20,07614 ms108 ms
Miss (screen + model)1,83094 ms265 ms
Blocked attack3,51084 ms236 ms

From 25,416 real requests. Screening every request throws this speed-up away — so the fix has to make the cache itself safety-aware.

What Phase 3 does

Let the cache ask a second question.

The cache today asks

“Does this sound like something I answered before?”

That is the only question. It is the hole.

SentryGate also asks

“...and was that earlier question safe?”

The label is already stored, so it is one extra check, no extra model.

Next milestone: rerun these exact attacks with the check on. The bypass rate should fall sharply — that is the first proof the fix works.
